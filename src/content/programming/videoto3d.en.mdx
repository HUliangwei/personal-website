## Overview

Videoto3D is a local-first video-to-3D reconstruction studio that integrates video ingestion, environment checks, frame extraction, subject segmentation, pose recovery, reconstruction, and result inspection inside a unified Run workspace.

Starting with V1.4, the project no longer treats every video as a variation of the same SfM problem. It provides two peer workflows based on the physical capture setup: **Orbit Camera** for a static object observed by a moving camera, and **Turntable** for a fixed camera observing a rotating rigid object.

## Features

- **Unified Run workspace**: each reconstruction uses an isolated `workspace/runs/<run_id>/` for source video, frames, masks, intermediate artifacts, logs, and final assets.
- **Capture-specific workflows**: Orbit Camera or Turntable is selected when a Run is created and remains fixed for that Run.
- **Video preprocessing**: FFmpeg frame extraction plus SAM2 subject masks and segmentation QA.
- **Stable Orbit Camera reconstruction**: full-RGB COLMAP incremental SfM keeps background texture available for camera pose recovery.
- **Turntable research workflow**: isolates fixed-camera / rotating-object reconstruction, preserves the V1.3 constrained-pose baseline, and leaves room for structured-essential, global-orbit, and SfM-free Gaussian research.
- **Dual outputs**: a Geometry Route produces GLB assets, while a Gaussian Route produces Gaussian Splat PLY assets.
- **Local Web Studio**: FastAPI with React/TypeScript for Run management, ROI selection, job logs, quality information, path inspection, and 3D previews.
- **Canonical CLI**: V1.4 standardizes the user entry point as `python Videoto3D.py ...`.

## Architecture

Videoto3D resolves the capture geometry when a Run is created rather than switching algorithms late in the sparse-reconstruction stage.

```text
Video + Capture Method
          |
          +-- Orbit Camera
          |      Static object / moving camera
          |      Full-RGB COLMAP incremental SfM
          |
          +-- Turntable
                 Fixed camera / rotating object
                 Turntable-specific pose research

          |
    Unified Run Workspace
          |
          +-- Geometry Route
          |      COLMAP / OpenMVS / Blender
          |      -> GLB
          |
          +-- Gaussian Route
                 Brush / future SfM-free research
                 -> PLY
```

COLMAP, OpenMVS, Brush, and Blender remain shared low-level infrastructure, while capture-specific behavior is isolated behind workflow boundaries. This prevents experimental Turntable pose work from changing the stable Orbit Camera reconstruction path.

## Key Implementation

### 1. Local-first workspace contract

All inputs, intermediate artifacts, caches, logs, and final outputs are kept inside the Videoto3D workspace. Project data is not written into the installation directories of COLMAP, OpenMVS, Brush, or Blender.

This makes individual Runs reproducible and inspectable while reducing accidental state leakage across external tools.

### 2. Decoupling Orbit Camera and Turntable reconstruction

V1.3 experiments exposed a fundamental difference between the two capture geometries. A fixed camera observing a rotating object is not just a parameter variation of standard moving-camera SfM. After background removal, angular motion has to be inferred from the object itself, which introduces weak constraints, multiple valid local solutions, and global trajectory inconsistencies.

V1.4 therefore promotes the two setups to peer workflows:

- `orbit_camera`: stable, full-RGB, standard incremental SfM.
- `turntable`: research-oriented, single-axis motion constraints, independent pose and trajectory estimation.

The V1.3 constrained-pose and adaptive-angle implementation is preserved as a research baseline for comparison instead of remaining embedded in the Orbit Camera path.

### 3. Independent Geometry and Gaussian outputs

Geometry and Gaussian Splat routes share Run management and result inspection, but their upstream algorithms are allowed to diverge.

The Geometry Route targets exportable GLB mesh assets. The Gaussian Route targets high-quality novel-view representations and leaves room for future Turntable reconstruction that does not depend on conventional SfM poses.

### 4. Shared core for CLI and Web Studio

Both command-line and Web Studio operations use the same Run and pipeline capabilities. The CLI supports reproducible debugging and automation, while the browser provides ROI selection, task progress, logs, artifact inspection, and interactive 3D viewing.

V1.4 standardizes the public command entry point as:

`python Videoto3D.py ...`

while `app.py` remains an internal implementation and compatibility layer.

## Challenges & Decisions

### Turntable pose recovery

In Turntable capture, the camera and background remain fixed while the foreground subject rotates. This conflicts with the conventional SfM assumption of a static scene observed by a moving camera.

Early experiments used SAM2 mask-guided features, a free-span angle graph, constrained Essential fitting, and known virtual-camera triangulation. Real runs showed that a low pairwise geometric residual does not guarantee the physically correct rotation angle: multiple angle hypotheses can explain the same correspondence set, causing sudden pose jumps, torn sparse geometry, and downstream degradation in both GLB and PLY reconstruction.

V1.4 therefore stops treating Turntable as a special flag inside ordinary sparse reconstruction. Future work focuses on a shared rotation axis, structured-essential constraints, cycle consistency, global-orbit refinement, and SfM-free Gaussian reconstruction.

### Isolating stable engineering from experimental research

The project needs both a reliable end-to-end video-to-3D engineering path and room to explore frontier Turntable reconstruction.

Instead of maintaining two independent applications, Videoto3D shares Run management, environment handling, viewers, and final asset organization while isolating capture-specific algorithms behind separate workflow boundaries. The stable path can be frozen while the research path evolves rapidly.

## Results & Next Steps

The project already provides local Run management, environment checks, video frame extraction, SAM2 segmentation, integration with COLMAP / OpenMVS / Brush / Blender, dual GLB / PLY outputs, and a Web Studio for task execution and 3D result inspection.

V1.4 is currently undergoing a **real-video Orbit Camera regression test** to confirm that the static-object / moving-camera workflow remains stable after the architectural split. Once validated, the new capture-workflow architecture will become the next stable project baseline.

Turntable development will then continue independently, informed by recent work on single-axis constrained pose estimation and SfM-free Gaussian reconstruction. Planned research UI additions include rotation-angle trajectories, shared-axis estimates, cycle-consistency diagnostics, and observability/confidence metrics.
